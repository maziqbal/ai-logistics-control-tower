
# AI Logistics Control Tower — Project Decisions

**Baseline:** Implementation Blueprint v1.0  
**Status:** Approved  
**Last reviewed:** 22 October 2026

This document tracks the project's architectural and domain decisions.
The approved [Blueprint](./BLUEPRINT.md) contains the detailed rationale.

## 1. Product and MVP Scope

- Build a portfolio-quality last-mile delivery operations platform.
- Initial operational setting: Europe.
- Primary user: dispatcher.
- Secondary user: driver through a responsive web portal.
- Demonstration target: 8 drivers and approximately 60 parcels.
- Initial implementation scenario: 2 drivers and 8–12 parcels.
- Solo development budget: approximately 10–15 hours per week.

**MVP includes:** manual dispatch planning, automatic road routing,
deterministic GPS simulation, live tracking, delivery execution,
rule-based alerts, operational summaries, tests, and deployment.

**Deferred:** route optimization, machine learning, agentic AI,
native mobile apps, multi-tenancy, and microservices.

## 2. Logistics Domain Rules

1. A route contains ordered stops.
2. A stop can contain multiple parcel deliveries.
3. The dispatcher manually assigns deliveries to routes and drivers.
4. The dispatcher manually determines stop order.
5. The routing engine calculates drivable road geometry and baseline ETA.
6. Route assignments and stop order are frozen during execution.
7. A delivery attempt requires an actual visit and attempt.
8. A skipped stop creates no delivery attempt.
9. Parcels at the same stop can have different outcomes.
10. A route can close with unresolved deliveries if all stops are
    completed or skipped.
11. Failed or skipped deliveries remain available for follow-up.
12. Delivery completion must be idempotent and transactionally safe.

## 4. Simulation Architecture

- GPS positions are generated by the backend, not real driver devices.
- Simulated vehicles follow calculated road geometry.
- Simulation uses a controllable simulated clock.
- Seeded scenarios must be reproducible.
- Frozen delivery plans are separated from execution state.
- Each simulation run owns its delivery outcomes, stop progress,
  route progress, location history, and alerts.
- Completed runs must not overwrite each other.
- The initial deployment supports one active run per backend instance.
- Simulation and driver actions must not independently complete
  the same parcel.
- External routing APIs must not be called on every GPS update.
- Interrupted runs must not silently resume with inconsistent state.

## 5. Data Integrity and Security

- PostgreSQL is the authoritative source of persisted state.
- Critical business mutations use database transactions.
- Use foreign keys, uniqueness constraints, and appropriate indexes.
- Protect delivery commands against duplicate submissions.
- Use locking or version checks for concurrency-sensitive operations.
- Validate requests and enforce role-based authorization.
- Publish WebSocket updates only after successful persistence.
- Clients must be able to resynchronize after missed events.
- Do not commit secrets or credentials.
- Use structured logging and audit records for important actions.

## 6. Provisional Decisions

These require validation before final approval.

### ORM

Drizzle ORM is preferred.

Validate:
- PostgreSQL/PostGIS compatibility.
- Migration workflow.
- Transaction and row-locking support.
- Spatial query ergonomics.

Prisma and TypeORM remain alternatives if the spike reveals
significant limitations.

### Routing Provider

Use an OSRM-compatible adapter.

Validate:
- Routing API capabilities.
- Road geometry quality.
- Request limits and licensing.
- Reliability and hosting cost.

Public demonstration endpoints are not production dependencies.

## 7. Deferred Infrastructure

Redis and BullMQ are deferred until a genuine background workload
requires durable asynchronous processing.

Do not use a generic job queue as the simulation clock.

Do not introduce Kubernetes, microservices, or event sourcing
without a demonstrated requirement and explicit approval.

## 8. Future Machine Learning

ML is planned after the operational MVP.

Requirements:
- Realistic and documented training/evaluation data.
- Clear prediction target and baseline model.
- Train/validation/test separation.
- Appropriate time-aware evaluation where relevant.
- Reproducible experiments and model versioning.
- Evaluation against simple non-ML baselines.
- Honest reporting of limitations and uncertainty.

Initial focus: ETA or delivery-delay prediction.

## 9. Future Agentic AI

Agentic AI is planned after the MVP and initial ML work.

Requirements:
- Clearly defined operational use cases.
- Explicit tool schemas and permissions.
- Read-only analysis by default.
- Human approval for state-changing recommendations/actions.
- Audit trails and observability.
- Evaluation of correctness and failure modes.
- Protection against prompt injection and unsafe tool execution.
- No unverified claims of autonomous operational capability.

## 10. Engineering Standards

- Strict TypeScript and explicit validation.
- Modular design with clear responsibilities.
- Unit, integration, and end-to-end tests.
- Real PostgreSQL/PostGIS integration testing.
- CI checks for linting, types, tests, and builds.
- OpenAPI documentation for HTTP endpoints.
- Document WebSocket event contracts.
- Meaningful Conventional Commits.
- Small, reviewable changes.
- Maintain README, roadmap, and ADRs.
- Prefer simple solutions over speculative abstractions.

## 11. Change Control

Approved decisions must not be silently replaced.

For any proposed change:

1. Identify the existing decision.
2. Explain the technical or product reason for changing it.
3. Compare viable alternatives.
4. Describe implementation and maintenance consequences.
5. Obtain approval before adopting the change.
6. Update this document and the relevant ADR.
